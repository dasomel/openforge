# OSS 공개 준비 표준

파일 존재 여부가 곧 외부 공개 준비 완료를 의미하지 않습니다. 어떤 저장소든 기존 OpenForge 지표(이중언어 문서 존재, CI 통과, LICENSE 커밋)를 모두 충족하고도 실제 첫 방문자나 첫 기여자 앞에서는 실패할 수 있습니다. 이 표준은 그 간극을 메웁니다.

> `dasomel/nfs-quota-agent`(기존 지표 기준 81.8%)를 대상으로 Claude·Codex(GPT)·Gemini(agy) 교차 모델 검증을 수행했습니다. 세 모델 모두 아래 6개 갭에 독립적으로 수렴했으며, 각 항목은 추측이 아니라 실제 저장소를 확인해 검증했습니다.

## 규칙

- **링크는 존재가 아니라 실제로 연결되어야 합니다.** `README-ko.md`가 존재하는지 확인하는 것만으로는 `README.md`가 `README_ko.md`를 가리키는 오류를 잡지 못합니다. 내부 마크다운 링크(및 주기적으로 외부 링크)를 CI에서 검증하세요 — 파일 존재 검사만으로는 부족합니다.
- **검색성 메타데이터를 파일뿐 아니라 실제로 게시해야 합니다.** 공개 저장소에는 GitHub `topics`, `description`, (권장) social preview 이미지와 homepage URL이 필요합니다. 이는 작업 트리 안에 존재하지 않으므로 파일 존재 감사로는 확인할 수 없습니다 — `gh repo view` / `gh api repos/<owner>/<repo>/topics` 등으로 별도 확인하세요.
- **Quickstart는 문서로 존재하는 것이 아니라 실제로 검증되어야 합니다.** README의 "Quick Start" 문구는 주장일 뿐 증거가 아닙니다. 가능하다면 깨끗한 환경에서 문서화된 절차대로 build/install/run을 수행하는 스모크 테스트를 CI에 연결해, quickstart 드리프트가 실망한 신규 사용자에게 발견되기 전에 자동으로 잡히게 하세요.
- **인바운드 기여에는 명시적 조건이 필요합니다.** 아웃바운드 라이선싱(`docs/oss-compliance.md`)과 인바운드 기여 조건은 다릅니다. 최소한 외부 PR에 대해 DCO(`Signed-off-by`)를 요구하세요. 정식 CLA는 포트폴리오 기본값이 아니라 프로젝트별 확대 조치입니다. 백로그 여건이 되면 신규 기여자를 위한 소수의 이슈에 `good first issue` 등 라벨을 붙이세요.
- **보안 공개(disclosure)는 템플릿이 아니라 실제로 작동해야 합니다.** `docs/security.md`는 취약점 보고 절차 게시를 요구하지만, 이 표준은 그 절차가 실제로 작동할 것을 요구합니다: 실질적인 비공개 신고 채널(GitHub Private Vulnerability Reporting 활성화 또는 실제로 연락 가능한 메인테이너 연락처 — 자리표시자 아님), 명시된 대응 시한, 지원 버전 정책. 48시간 대응을 약속하면서 실제로 닿을 수 있는 채널이 없는 `SECURITY.md`는 아무 약속도 없는 것보다 나쁩니다.
- **행동강령(CoC) 집행에는 실제 연락 창구가 필요합니다.** 이름·주소·양식 없이 "커뮤니티 리더"라는 미정의 대상에게 신고하라는 CoC는 집행 불가능합니다. 단독 메인테이너 프로젝트라도 실제로 연락 가능한 신고 경로를 명시하세요(`docs/maintainer-governance.md` §1 참고).
- **공개 게시 적격성 확인은 필수 파일이 아니라 판단의 문제입니다.** 저장소를 공개로 전환하기 전, 메인테이너는 상표권·수출통제·제3자 개인정보 관련 장애 요소가 없는지 간단히 자체 확인해야 합니다. 이는 경량 자체 확인(self-attestation) 절차이지 문서 요구사항이 아닙니다 — 이를 위한 필수 파일을 새로 추가하지 마세요.

## 포트폴리오 전체에 명시적으로 요구하지 않는 항목

`CITATION.cff`와 `FUNDING.yml`은 연구 인접 프로젝트나 후원을 받는 프로젝트에는 타당하지만, 두 모델 모두 이를 인증 게이트가 아니라 프로젝트별 판단 사항으로 판정했습니다. 이 항목들의 부재를 컴플라이언스 갭으로 표시하지 마세요.

## 이미 다른 곳에서 다루는 영역 — 중복 금지

릴리스 무결성(`docs/release.md`), 메인테이너 거버넌스(`docs/maintainer-governance.md`), 기본 OSS 법적 컴플라이언스(`docs/oss-compliance.md`)는 독립적으로 검토한 결과 충분한 것으로 확인되었습니다. 이 표준은 위 문서들이 다루지 않는 부분만 추가합니다.

## 자동 감사와의 관계

`templates/scripts/audit-portfolio.py`는 현재 파일 존재 여부만 채점하며, 위 규칙 중 어느 것도 평가할 수 없습니다(링크가 실제로 연결되는지, GitHub API 호출이 성공하는지, quickstart가 실제로 작동하는지는 파일시스템만으로 알 수 없는 사실입니다). 감사 엔진이 이를 검증할 수 있게 확장되기 전까지는 이 문서를 수동/CI 보완 가이드로 취급하고, 포트폴리오 점수가 높다고 해서 이 표준을 준수한다고 가정하지 마세요.
